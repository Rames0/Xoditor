# Xoditor 2.0 architecture and delivery plan

## Current repository

The source entry and enhancement layer implement a contenteditable editor.
The enhancement layer overrides parts of the base editor. The browser package
concatenates these files with CodeMirror and Prettier, then minifies the result.
CSS, fonts and third-party notices ship separately. The public playground and
table reference use the browser bundle. GWP uses a separate optional adapter.

| Area | Existing implementation | Remaining gap |
|---|---|---|
| Commands and selection | Ribbon, browser selection, text styles, lists, links, images, tables | Browser-dependent commands, duplicated implementations, no shared model or transaction boundary |
| History and clipboard | HTML snapshots, selection recovery, Office HTML cleanup, source mode, clipboard images | Real Word and Google Docs coverage, incremental history, explicit transaction grouping |
| Documents | Page size, margins, orientation, page breaks, print HTML, template CSS | Pagination engine, repeated page furniture, direct PDF output, DOCX conversion, section breaks and a template library |
| Nepali | Unicode editing, bundled fonts and mixed-script tests | Font redistribution audit, native IME tests, locale formatting and a verified Bikram Sambat adapter |
| Extensibility | Constructor options, callbacks, multiple instances and lifecycle | Complete plugin surface, framework examples, typed configuration and stable event contracts |
| Security | Import filtering, URL checks, separate application sanitization guidance | Review all rendering boundaries, validate uploads by content, define trusted template CSS handling and commission independent review |
| Collaboration | Local autosave and undo history | Shared document model, concurrency, comments, suggestions and external authorization |
| UI | Responsive ribbon, contextual controls, keyboard shortcuts and automated accessibility scans | Theme system, touch workflows, manual assistive technology tests |
| Packaging and performance | Static Vercel build, minified assets, source/browser tests | Optional lazy bundles, repeatable latency and memory measurements, release packaging |
| Quality | Browser matrix, clipboard fixtures, playground UI tests, accessibility and Office comparison | Native app clipboard evidence, real mobile devices, complete release verification |

## Delivery order

1. Establish a compatible module and extension API. Keep the current browser
   entry stable and test both entry points.
2. Extract selection, commands, clipboard and serialization behind the existing
   interfaces. Migrate one command family at a time. Establish transaction
   grouping and history before introducing collaborative document operations.
3. Build document layouts and templates on the stable serialization contract.
   Keep DOCX and PDF conversion optional and test against representative files
   before declaring fidelity. Host services may provide conversion and storage.
4. Add Unicode and locale fixtures, verify font distribution rights, and expose
   date conversion through a host-provided adapter with explicit calendar range.
5. Extend plugins with toolbar and keyboard registration, build framework examples,
   then add responsive themes and keyboard and touch testing.
6. Define a versioned collaboration protocol after document transactions are
   stable. A host must supply authentication, storage and permission enforcement.
7. Run security, accessibility, bundle and browser release checks. Publish a
   major version only after migration and compatibility checks pass.

## First increment

The optional browser ES module exposes scoped command registration, change
subscriptions and plugin cleanup. It delegates editing, history and serialization
to the current editor. The npm module entry has TypeScript declarations. The
classic script and its global constructor continue to use the existing API.

The module is a browser entry and currently loads the same bundled editor.
The longer-term core split and lazy loading require separate build work.
